# SecScan

> **Repository identity.** This repo (`VibeScan-Enterprise-Build`, originally
> VibeScan) is **SecScan**, deployed at **secscan.us**.
>
> It is **not** Seclayer. Seclayer is a separate product in a separate repo
> (`seclayer.io2026`, deployed at seclayer.app) with no shared git history.
> Seclayer is the higher tier: it adds real nmap port/service scanning and
> red-team attack modules, neither of which exists here. SecScan's port scan is
> a TCP-connect sweep over 33 common ports (`artifacts/api-server/src/lib/recon.ts`).
>
> The two launch separately. Never deploy one to the other's Railway service.

Black-box web security scanning that produces a plain-English report.

Point SecScan at a URL and it probes the live site from the outside — no
agent, no source access, no credentials — then grades what it finds A–F and
explains each issue in language a non-specialist can act on. Every scan adds a DeepSeek-generated analysis and a
paste-ready fix prompt that works in any AI coding tool (it uses the stack the scan detected for where fixes live, and names no tool).

It was built for people shipping apps faster than they can audit them: sites
generated by AI builders, Supabase/Firebase backends wired up in an afternoon,
side projects that quietly went to production.

> **Pricing.** Every account gets 3 free scans a month (renewing on the 1st,
> UTC). Beyond that there is one plan, **SecScan Unlimited**, $19/month: unlimited
> full scans (fair use: the per-account rate limits still apply, 5 an hour and 20 a
> day by default) and monitoring of up to 5 sites. Credit packs are no longer sold
> (a balance already held still spends, and an old paid checkout is still credited);
> Starter and Pro stay in the plan table, not sold, so a row carrying one still
> resolves. The price lives in code, `lib/plans.ts`, and checkout builds the Stripe
> price from it; `lib/stripe.ts` keeps the pack grant table and `PACKS_ON_SALE`. Payments are on
> exactly when `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are set; see
> `deploy/PAYMENTS-GO-LIVE.md`. Monitoring stays free for everyone until
> `MONITORING_REQUIRES_PLAN=true`. Once it is set, an account with no plan keeps
> one watched site (`FREE_MONITOR_SITES`, default 1; 0 turns it off), rescanned
> no more often than weekly. Accounts already monitoring more are grandfathered
> by `scripts/grandfather-monitor-users.ts`, which must run first.

## What it checks

**158 distinct checks on every website scan**, and a repository scan runs its own 56 (214 in the catalogue in total). The two sets differ because they are different scans: `lib/checkCatalog.ts` itemises both, and `checkCatalog.test.ts` pins the counts. There are no tiers — `routes/scans.ts`
pins every run to the full suite (`const tier = "deep" as const`) and the
OpenAPI `ScanRequestTier` enum has a single member. `basic` survives only so
scans recorded before the tier was retired stay readable.

A check is one piece of detection logic. The lookup tables (the sensitive-path
list, the secret patterns, the takeover fingerprints, the crawled paths) hold
signatures, not separate checks: one path probe applied to 81 paths is one check. The counting method is written up
in `src/data/coverage.ts` in the secscan.info repo, which renders this list
publicly.

What varies between two scans is **access, not tier**:

| Gate | Unlocks |
|---|---|
| Domain verification (DNS TXT or well-known file) | The offensive active probes (listed under "Scan only what you are allowed to scan" below) — without it, the passive checks only |
| Credentials | The surface behind the login |
| A second account | Broken access control (A01) |
| An OOB collector (`OOB_BASE_URL`) | SSRF detection (A10) |

Coverage spans: HTTP
response headers and cookie flags, TLS (the scanner's own check of protocol
versions, certificate validity and trust, key size and cipher suite; a Qualys SSL
Labs grade only if `SSLLABS_ENABLED=true`), DNS and email authentication (SPF/DMARC/DKIM/DNSSEC), technology
fingerprinting (~60 technologies), active HTTP path probes, known-CVE version
matching, JWT analysis, subdomain takeover, vibe-stack database exposure
(Supabase RLS, open Firebase rules), source-map exposure, JavaScript secret
scanning, path traversal, and a 20-page site crawl that re-runs the header and
cookie checks on each page.

**[`SCAN_COVERAGE.md`](SCAN_COVERAGE.md) enumerates them** — each check, its
severity, and which tier runs it. (It documents the probe modules; the TLS
checks, which live in the scan worker, aren't listed there yet.)
[`SCAN_TESTS.md`](SCAN_TESTS.md) describes the method behind each check, not how
it was validated. The validation evidence is in `artifacts/api-server/scripts/`:
[`SCAN-RESULTS.md`](artifacts/api-server/scripts/SCAN-RESULTS.md) (what the
scanner returned for each measured run),
[`FALSE-POSITIVE-AUDIT.md`](artifacts/api-server/scripts/FALSE-POSITIVE-AUDIT.md)
(the false positives found and fixed), and
[`RETEST.md`](artifacts/api-server/scripts/RETEST.md) (the procedure, run by hand
with `scripts/live-scan.ts`). None of it runs in CI.

Findings are scored `Critical +30 / High +15 / Medium +5 / Low +1` into a risk
score, which maps to a letter grade (A: 0–10, B: 11–25, C: 26–45, D: 46–65,
F: 66+).

### Signal quality is the point

A scanner that cries wolf teaches people to ignore it, so suppression rules are
treated as a first-class feature rather than an afterthought — SPA and
multi-tenant catch-all detection, structural markers instead of keyword
matches, entropy thresholds on secret patterns, session vs. non-session cookie
classification, and public-by-design keys (`pk_live_`, `sb_publishable_`,
Firebase `AIza…`) never flagged on their own. The rules every new probe is
expected to follow are written up in
[`ENGINEERING.md`](ENGINEERING.md#scanner-false-positive-prevention).

## Use from AI editors (MCP)

`POST /api/mcp` is a remote, stateless MCP server (Streamable HTTP) authenticated
by personal API tokens that users create in Settings → AI editors. Tools:
`scan_url`, `get_scan_status` (optionally waits up to 60 s), `get_report`,
`list_recent_scans`, `list_verified_domains`.

- **No side door.** `scan_url` runs the website's own `createScanHandler` after
  its own rate limiters (`routes/scans.ts`), so trial, credits, plan scans, the
  SSRF guard and domain-ownership gating apply unchanged.
- **Tokens are MCP-only.** `ssk_…`, 256-bit, stored as SHA-256, revocable. The
  site's auth middleware never accepts them, so a leaked token cannot touch
  account, billing or token routes.
- End-to-end check: `artifacts/api-server/scripts/verify-mcp.mjs` (writes test
  data — throwaway database only).

## ⚠️ Scan only what you are allowed to scan

Scans send active probes — traversal attempts, injection canaries, forged-origin
and unusual-method requests, out-of-band SSRF callbacks, a TCP port scan. Running
them against infrastructure you neither own nor have written permission to test
is likely illegal in your jurisdiction and violates most providers' terms of
service. You are responsible for your targets.

This is enforced, not just requested: `lib/activeProbeGate.ts` decides for each
scan whether the active probes may run, and it allows them only once the user has
proven control of the target domain (or the operator has unlocked the instance).
It fails closed on any lookup error.

Which probes are gated, and why:

- **Gated** (only when the gate allows): the probes that send a crafted request
  to the target — HTTP method and CORS checks with a forged `Origin`, open
  redirects, path traversal, reflected-XSS and error-based SQLi probes, API
  endpoint testing, the out-of-band SSRF test, the Supabase and Firebase row
  probes, the prompt-injection and race-condition tests, the cross-account
  checks, the checkout price test, and the TCP port scan.
- **Ungated, by design**: requests any crawler or search engine would make. These
  are the sensitive-file path list, `robots.txt`, `security.txt`, directory
  listings, the API-documentation and health-endpoint paths, the site crawler,
  the subresource-integrity, header, cookie and TLS checks, the subdomain-takeover
  lookups, and DNS and subdomain enumeration (public records only). Fetching a path,
  even one nothing links to, is what every crawler does, and a passive check reads
  the answer without sending anything unusual. Each of these runs for any target.

## Architecture

A pnpm-workspaces monorepo. React front end, Express API, PostgreSQL, and an
in-process job queue — a scan is a queued job, not a request you hold open.

```
artifacts/
  api-server/       Express 5 API — src/routes, src/lib (the scan engine), src/middlewares
  vibescan/         React 19 + Vite front end — src/pages, src/components
lib/
  api-spec/         openapi.yaml — the API contract source of truth
  api-zod/          Zod schemas generated from the spec
  api-client-react/ Generated API client
  db/               Drizzle schema + migrations
```

- **Stack**: React 19, Vite 7, Tailwind, Wouter, TanStack Query / Express 5,
  TypeScript ESM, pino, pg-boss / PostgreSQL 16 via Drizzle ORM / esbuild.
- **Accounts.** Sign-up is two steps: details, then a six-digit code emailed to
  the address, so no account exists until the email is proven. `routes/account*.ts`
  handles register, login, email verification, password reset/change and deletion,
  and `routes/googleAuth.ts` handles Google OAuth. Sessions are cookies. The old
  anonymous `Authorization: Bearer <user id>` path honours only rows that already
  exist (an unknown id creates nothing) and can be closed with
  `LEGACY_BEARER_SUNSET` or `ALLOW_LEGACY_ANONYMOUS_BEARER=false`; registering
  promotes such a row in place. Daily scan quotas are `SCAN_DAILY_LIMIT_ANON` (10)
  and `SCAN_DAILY_LIMIT_ACCOUNT` (50).
- **Two processes, one image.** `src/index.ts` (the `web` tier) serves
  the API and the built frontend and only *enqueues* scans. `src/secscan.ts`
  (the scanner) runs the pg-boss worker, the monitor scheduler and the EOL/CVE
  refresh, and owns Chromium. They share nothing but the `scan-job` queue in
  Postgres, which is what lets them scale separately and keeps Playwright out of
  the web image. `docker-compose.yml` brings up both; on Railway they are two
  services off the same Dockerfile with different start commands — see
  [`deploy/railway/NOTES.md`](deploy/railway/NOTES.md), which records what
  happens when the web service accidentally boots the scanner's entrypoint.
- **Everything external degrades gracefully.** DeepSeek, Resend, and Stripe each
  check for their key at startup and log a warning if absent; the app stays
  functional without any of them.
- **Credentials are encrypted at rest and discarded after the scan.** A
  credentialed scan holds a customer's live login, so `lib/crypto.ts` seals it
  with AES-256-GCM under `ENCRYPTION_KEY`, and the worker nulls the column on
  both the success and the failure path — the credentials live exactly as long
  as the scan that needed them. Storing them requires a registered, verified
  account; an anonymous UUID is not enough.
- **Monitoring is risk-adaptive.** Rescan cadence follows the grade — A every 14
  days, B/C every 7, D/F every 3 — with Slack-compatible webhooks for CVE
  alerts, regressions, and certificate expiry.

## Getting started

**Prerequisites:** Node 22.9+ (24 recommended), pnpm 10, PostgreSQL 16.

```bash
pnpm install

# Shared libs use TypeScript project references — their dist/*.d.ts is what
# typecheck actually reads, so build them once on a fresh clone.
pnpm --filter @workspace/db run build
pnpm --filter @workspace/api-zod run build
pnpm --filter @workspace/api-client-react run build

cp .env.example .env    # then fill it in — see below
```

Push the schema to your database (drizzle-kit reads the shell environment, not
`.env`):

```bash
DATABASE_URL=postgresql://... pnpm --filter @workspace/db run db:push
```

Then run the two servers in separate terminals:

```bash
pnpm --filter @workspace/api-server run dev   # API on $PORT (use 8080)
pnpm --filter @workspace/vibescan run dev     # front end on 18425
```

The front end proxies `/api` to `localhost:8080`, so keep `PORT=8080` in
`.env` — and set it *there* rather than exporting it in your shell, or the Vite
dev server will try to bind the same port. Health check: `/api/healthz`.

Optional: `pnpm exec playwright install chromium` enables headless rendering of
JavaScript-heavy SPAs. Without it, scans fall back to raw fetch and log a
warning.

### Configuration

`.env` at the repo root is loaded by the API server via Node's
`--env-file-if-exists`. Real environment variables take precedence, so the file
is simply ignored in environments that inject their own. It is gitignored;
don't commit it.

| Variable | Required | Purpose |
|---|---|---|
| `PORT` | **yes** | API server refuses to boot without it. Use `8080` locally. |
| `DATABASE_URL` | **yes** | PostgreSQL connection string. |
| `DEEPSEEK_API_KEY` | no | Fallback AI analysis when a user hasn't set their own key. |
| `ENCRYPTION_KEY` | no | 32-byte base64 AES-256 key that seals scan credentials at rest. Without it, credentialed scanning is unavailable; anonymous scanning is unaffected. |
| `RESEND_API_KEY` | no | Email notifications (report ready, CVE alerts). |
| `APP_ORIGIN` | no | Base URL for links in emails. No trailing slash. |
| `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` | no | Payments are on exactly when both are set; unset, the pricing page shows "not live yet". See `deploy/PAYMENTS-GO-LIVE.md`. |

Generate an encryption key with:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

## Development

```bash
pnpm run typecheck                              # whole workspace
pnpm run build                                  # typecheck + build every package
pnpm --filter @workspace/api-server run test    # ~3,000 tests; the database-backed suites skip without Postgres
pnpm --filter @workspace/vibescan run test
```

After editing `lib/api-spec/openapi.yaml`, regenerate and rebuild the
downstream packages — typecheck reads their emitted `.d.ts`, not their source:

```bash
pnpm --filter @workspace/api-spec run codegen
pnpm --filter @workspace/api-zod run build
pnpm --filter @workspace/api-client-react run build
```

[`ENGINEERING.md`](ENGINEERING.md) is the working engineering doc: the false-positive
rules new probes must follow, plus the accumulated gotchas — why some helpers
are deliberately duplicated between `scanner.ts` and `crawler.ts`, why Vitest
`fetch` mocks need `vi.stubGlobal`, and other things worth knowing before your
first change.

Key entry points:

| | |
|---|---|
| Scan engine | `artifacts/api-server/src/lib/scanner.ts` |
| API routes | `artifacts/api-server/src/routes/index.ts` |

## Deployment

**[`DEPLOY.md`](DEPLOY.md) is the full guide** — Docker Compose onto any Linux
host, with DNS, TLS, backups and the caveats worth knowing before taking real
traffic.

```bash
cp .env.docker.example .env.docker   # set POSTGRES_PASSWORD, ENCRYPTION_KEY, APP_ORIGIN
docker compose --env-file .env.docker up -d --build
```

That brings up PostgreSQL, the `web` tier, the `secscan` scanner and a backup
service. Both app tiers apply pending migrations on boot. TLS is **not** part of
the stack: `web` is published on `127.0.0.1:8090` only, so put a reverse proxy
(Caddy, nginx) in front of it — see [`DOCKER.md`](DOCKER.md). The scanner image
installs Chromium at the Playwright version pinned in the Dockerfile.

`APP_ORIGIN` is a **build** argument as well as a runtime one: the frontend
bakes it into canonical links, Open Graph tags, JSON-LD and the sitemap, so
changing the domain means rebuilding the image.

Deploying without Docker: build the front end and API, point
`FRONTEND_STATIC_DIR` at `artifacts/vibescan/dist/public`, and run
`node artifacts/api-server/dist/index.mjs` behind a TLS-terminating proxy.
Never set `NODE_TLS_REJECT_UNAUTHORIZED=0` in production.
